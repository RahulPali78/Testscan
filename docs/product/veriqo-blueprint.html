01

The complete product in plain English

Connect applications and agents; test complete workflows and verify the actual outcome.

The product acts like a practice customer and an independent inspector. It interacts with applications and agents, follows a defined business workflow, checks what actually happened and gives developers evidence when expectations fail.

The final product goal

Customers integrate their supported applications and AI agents, define correct outcomes and run complete tests across systems. Web, APIs, AI agents, Android/iOS, desktop and voice are required parts of the implementation. A narrow support example is an engineering fixture, not the final product boundary.

What customers provide

Authorized application builds/endpoints, safe test identities, approved fixtures, platform access and business expectations. Authoritative observers are required for claims about backend state.

What customers receive

Passed, failed, inconclusive or explicitly not-tested outcomes; correlated actions and evidence; exact tested identities; reproduction inputs and release integration.

Three complete journeys

  • A mobile user asks an agent to create a ticket. Verify exactly one correct record exists, then confirm it in the web portal.
  • A desktop workflow asks an agent to update an account. Verify authorization and final API state, then confirm the result in another application.
  • A caller interrupts and corrects a voice request, then the agent hands it off. Verify retained intent, one authorized action and the resulting visible state.

What autonomy means

After permissions, fixtures and expected outcomes are approved, routine execution, observation, evaluation, evidence collection and configured release checks run unattended. People own business intent, permission grants, reviewed expectation changes and application fixes. A finite passing suite is evidence about tested scenarios and versions, not proof that every defect is absent.

Reforecast triggers

  • Native automation, device provisioning or voice transport cannot meet the required contract without additional engineering.
  • Authoritative observation, cleanup or stable candidate identity is unavailable for a committed workflow.
  • Actual effort, role bottlenecks or critical findings consume planned reserve.
  • A new platform version, protocol or capability is proposed: add explicit tasks and acceptance evidence rather than hiding it in existing estimates.

Scope boundary: required application classes remain in the complete implementation until the product owner explicitly changes the supported-product contract. Embedded/IoT hardware certification, arbitrary uploaded executable code, custom model training, autonomous production changes, and exhaustive security/load certification are separate product extensions. Enterprise SSO/SCIM is an optional enterprise extension; core tenancy, RBAC, audit, private runners and retention are required.

Fair comparison protocol

Benchmark representative web, mobile, desktop, voice and agent workflows against capable DIY configurations and relevant existing vendors. Give each tool a competent setup and equivalent assertions. Keep assessment cases withheld from tuning; retain all attempts and unresolved disagreements. Measure queue and execution separately. Execution semantics and reliability

Predictable behavior across retries, cancellation and application boundaries.

Execution status, correctness verdict, evidence completeness and cleanup status are separate dimensions across every application class. All platform branches share these semantics.

Execution stateBehavior
QUEUED → PREPARINGFreeze all bindings/candidates, validate eligibility and reserve capacity before preparing fixtures and sessions.
RUNNING → EVALUATINGExecute allowlisted steps under shared and per-target budgets; correlate observations without inventing missing telemetry.
CLEANING → FINISHED / ERROR / CANCELLEDReconcile in-flight effects, compensate owned resources and publish immutable execution evidence; cleanup retries append attributable events.
VerdictMeaning
PASSAll mandatory checks passed on the attested candidate set with complete required evidence.
FAILA required assertion or approved threshold failed with sufficient evidence; a later pass does not erase the failure.
INCONCLUSIVEWithout a witnessed required failure, required evidence or trustworthy execution is missing.
NOT_TESTEDExplicitly excluded optional capability/case; disclose the exclusion in coverage. Mandatory unsupported work is rejected at admission.
  • Commit run creation and outbox in one transaction; scoped idempotency keys reject changed payloads.
  • Use stable operation IDs across operational retries; target idempotency or authoritative reconciliation is required for external writes.
  • Fence task results by attempt/lease; keep late evidence without accepting stale completion.
  • Cancellation stops new actions and reconciles outstanding ones. Remote work may continue, so immediate cleanup success cannot be assumed.
  • Poll authoritative state through the declared observation window. A first matching record is insufficient evidence against a delayed duplicate.
  • Enforce tenant fairness, exclusive device/desktop leases, in-flight reservations and bounded queue admission; account for all chargeable attempts.
